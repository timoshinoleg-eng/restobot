# RestoBot MVP Scope

Дата: 2026-04-29
Статус: Working baseline
Владелец: Codex

## 1. Цель MVP

За 2 недели подготовить коммерчески понятный и технически воспроизводимый MVP `RestoBot`, который можно:

- показать 1-2 пилотным ресторанам;
- развернуть в Yandex Cloud без ручной правки инфраструктуры;
- продемонстрировать через единый сценарий `меню -> заказ -> смена статуса`;
- упаковать как отдельное направление на `chatbot24.su`.

MVP не должен пытаться закрыть весь ресторанный контур. Его задача — доказать спрос, понятность оффера и работоспособность пилотного сценария.

## 2. Целевая аудитория

Первичный сегмент:

- малые и средние рестораны;
- кафе;
- доставка еды;
- dark kitchen;
- локальные сети до 3-5 точек.

Первичный buyer:

- владелец;
- управляющий;
- операционный менеджер.

Входной канал:

- Telegram.

## 3. Обязательный продуктовый контур

В MVP входят только функции, без которых нельзя показать ценность.

### 3.1 Admin flow

- создание tenant ресторана;
- безопасный onboarding через защищенный bootstrap flow;
- загрузка меню;
- просмотр списка заказов;
- обновление статуса заказа.

### 3.2 Client flow

- создание widget/client session;
- просмотр меню;
- создание заказа;
- получение актуального статуса заказа.

### 3.3 Demo/operations flow

- один demo tenant;
- demo menu;
- smoke test после deploy;
- краткая инструкция для ручного пилотного запуска.

## 4. Что НЕ входит в MVP

Следующие вещи сознательно исключаются, даже если архитектурно они интересны:

- сложные модификаторы и конструктор блюда;
- варианты порций как полноценный продуктовый слой;
- AI-генерация описаний блюд;
- полноценная loyalty-система;
- бронирование столов;
- вызов официанта;
- складской контур и остатки;
- сложная аналитика;
- enterprise-grade role model beyond current pilot scope;
- полноценный aiogram catalog UX;
- multi-channel lead capture beyond Telegram.

## 5. Коммерческая рамка MVP

Основной оффер:

- ресторанный бот по подписке;
- первый месяц бесплатно;
- быстрый запуск;
- Telegram-first;
- акцент на хранение и обработку данных в российском контуре.

Пока не обещаем:

- “полную автоматизацию ресторана”;
- “замену сайту, CRM, POS и доставке одновременно”;
- мгновенную интеграцию со всеми системами;
- enterprise security beyond what реально готово в пилоте.

## 6. Техническая рамка MVP

Опорный репозиторий:

- `restobot`

Опорный cloud контур:

- Yandex Cloud
- Serverless Containers
- API Gateway
- Managed PostgreSQL
- Managed Redis
- Lockbox
- Terraform

Обязательные свойства:

- воспроизводимый deploy;
- smoke after deploy;
- без hardcoded secrets;
- без ручных правок в облачной консоли как части нормального процесса.

## 7. Scope decisions по menu-направлению

Подход к menu-domain:

- не интегрировать целиком внешний swarm-модуль как есть;
- использовать его как reference/backlog source;
- брать только те правила и сущности, которые реально нужны в первом пилоте.

В MVP по меню нужны:

- категории меню;
- блюда;
- цена;
- доступность;
- сортировка;
- изображение по URL;
- базовая валидация загрузки меню.

В MVP по меню пока не нужны:

- deep category tree;
- dietary tags как самостоятельный слой;
- variants;
- YandexGPT enrichment;
- сложный bot catalog navigation.

## 8. Definition of Done для MVP

MVP считается готовым, если одновременно выполнены все пункты:

- опубликована отдельная страница `RestoBot` на `chatbot24.su`;
- есть рабочий cloud deploy в YC;
- есть один demo tenant;
- onboarding ресторана работает без ручной правки БД;
- загрузка меню работает;
- клиент может создать заказ;
- админ может сменить статус заказа;
- smoke test проходит;
- есть понятный Telegram CTA для заявок;
- есть краткая operator-инструкция для запуска пилота.

## 9. Открытые решения

Эти решения пока не считаются закрытыми и будут уточняться после возврата исследований:

- точная pricing model после первого месяца;
- final messaging для `152-ФЗ` в лендинге;
- restaurant-specific competitor positioning;
- приоритет следующих vertical features после первого пилота.
